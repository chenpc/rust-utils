Agent 敢犯錯，系統程式才寫得動 — 沙箱就是那道容錯空間 · rust-dist · 2026-10-13

核心主張：agent 開發＝試錯，系統程式的試錯很貴

這 115 支直接動真實世界

  • rm/mv/mknod/dd/shred：檔案系統與裝置節點
  • chroot/kill/timeout：行程與排程
  • date -s：settimeofday(2) 系統時鐘
  • stty：terminal 的 termios

寫錯 syscall、無限迴圈、誤刪、把鐘調到 1970，都是開發過程的正常產物 — 在 host 上試錯，成本是資料、權限、時鐘、終端機。

解法：可丟棄的 QEMU 沙箱（人建的，不是 agent 建的）

  • 128 MB RAM、5.7 MB initramfs、開機就绪 ~0.9 秒、用完 sysrq power_off
  • 真實 Linux 核心、真實 syscall、真實 errno、root 權限 — 不是 mock
  • 沒有 busybox：/init 與 /bin/sh 都是我方 coreutils 的 applet；guest 內的 "cat"/"env" 由 symlink multi-call binary 自建
  • virtio-9p 雙通道：/mnt 唯讀（test binary）、/out 可寫（profraw 證據）
對 agent 透明：.cargo/config.toml  →  runner = scripts/qemu_runner.sh
  agent 眼中只是「cargo test」；每個 test binary（靜態連結）都被送進一台新 guest 執行
  profraw 經 9p 回到 host → llvm-profdata / llvm-cov → logs/<applet>.cov.out（門檻 80%）

危險的「後果」封在沙箱裡，危險的「行為」照常發生 — 於是每次錯誤的價格＝0.9 秒重開一台。

容錯空間實例 ＋ 開發中途加裝的三層護欄

沙箱內做得到、host 做不到實例
特權路徑「可測」而不是「要 mock」date -s 實測 settimeofday 成功路徑（guest 用完即丟）；mknod 真建裝置節點；chroot 到 tmpfs 新根；root 擋不住的 EISDIR 反而是可測性
agent 的真 bug 只燒沙箱timeout.rs 短旗標漏 k += 1 → timeout -p 0.2 sleep 30 無限迴圈燒滿 guest，被外层 timeout 收掉；代價＝一次重開＋一條 dev log（順帶掃全 repo 22 處同型迴圈）
destructive 測試全開rm/mv/truncate/shred 的破壞路徑在 tmpfs 工作目錄亂玩，亂完就關機

① Agent 指令執行逾時

全量回归常超過 agent 工具的指令時間上限 → 裝 pi package npm:@mrclrchtr/supi-bash-timeout 取消 bash 層預設逾時；長工作改背景＋輪詢 log。

② QEMU 掛死

test binary 掛死時 qemu 自己不會結束 → 每次開機包硬逾時 timeout --foreground -k 5 ${TIMEOUT_SEC:-120} "${qemu_cmd[@]}"；最壞就是 TERM→KILL 整個 qemu。

③ 平行執行 OOM

host 端 ulimit 限單行程虛擬記憶體；QEMU 天然 RAM 保護：每台 guest -m 128M → 平行度算進預算（N workers × 128M）。

同一個模式：發現一層新的失敗模式，就把防護裝進基礎設施，而不是要求 agent 更小心。

沙箱之上的驗收：門檻不可降、報告由證據產生

規格外部化（行為模型只從 man page）

  • 105 份本機 mirror ＋ 10 份 web search（URL＋SHA512 登記於 SOURCES.tsv）；GNU 與 uutils 衝突以 GNU 為準
  • man 未定義的邊界 → 我方「決定＋記錄」進 docs/assumptions.md（19 節 625 行），不猜、不追参考實作逐 byte
  • 禁止閲覧 reference source code；每個 applet 檔頭寫「規格來源＋我方決定」

機械式驗收

  • coverage ≥80% 不降門檻：不足就補測試（chroot 67.3% → 81.9%）；實際 115/115 達標、avg 91.0%
  • 115/115 fuzz：只断言 man 可推導的不變量 — date epoch round-trip、factor 因子連乘積==n、stty -g 自我解析、任意垃圾不 panic
  • docs/final_report.md 由 scripts/gen_report.py 從 logs/ 產生 → 與 checklist 逐條一致、gaps=0（寫的報告會過期，產生的報告不會）

最終成績：guest 全量 PASS=118 / FAIL=0（guest 階段僅 96 秒，-j 2 平行）；跳過清單：空。

方法論 ＋ 結論

  1. 先建沙箱，再寫程式：錯誤的價格決定 agent 能寫多大的系統
  2. 把沙箱接進工具鏈（cargo runner 層）→「在 guest 內跑」對 agent 透明，沒有一步需要「記得去沙箱」
  3. 護欄也是產出的一部分：指令逾時（supi-bash-timeout）、QEMU 硬逾時、ulimit＋-m 記憶體預算 — 發現一層失敗就裝一層
  4. 免 root、可搬移的 toolchain：apt 依賴探索一次 → manifest.tsv（URL+SHA512）→ curl 重製 → dpkg-deb -x 解進 .rust-env/.qemu-env/.llvm-env/.guest-env → git clone ＋ setup 就能在另一台（含無 root）機器完整重現開發與驗證
  5. 門檻不可協商：不足就補測試，不補說法；驗收全部機械化（guest PASS／coverage%／fuzz 不變量／報告由腳本產生）
  6. 所有進度落地成檔案：goal 任務樹、checklist、assumptions、development-log（57 條）、events.jsonl、logs/*.cov.out — 58 小時跨 session 靠檔案接力，不靠上下文；委派 subagent 要契約化，長迴圈與共用資源留主行程

AI agent 寫系統程式的瓶頸不是智商，是錯誤的價格。
把每次錯誤壓成「0.9 秒的一台可丟棄機器」之後，115 支直接操檔案、裝置、時鐘、行程的 coreutils，才能在 58 小時內安全地寫完並全數驗證。
